# Desain Prompt-first untuk Chat Generator Website

Status: disetujui pengguna untuk implementasi bertahap; Task 1 extractor dan corpus sedang disiapkan
Tanggal: 16 Oktober 2026
Perubahan ini memperbarui alur intake yang disepakati pada `2026-10-15-generator-chat-application-design.md`. Kontrak ekstraksi dan corpus train/development sudah dibuat. API, UI, dan checkpoint extractor belum diintegrasikan.

## Masalah yang terlihat

Setelah pengguna mengirim prompt, `ChatShell.sendPrompt` membuat `RequestDraft` kosong lalu meminta validasi. `prepare_intake` hanya memeriksa draft dan bukti fakta. Ia tidak mengekstrak fakta dari teks prompt. Karena itu UI menampilkan `BusinessFactsForm` yang meminta nama, deskripsi, keunggulan, tiga layanan, tiga langkah proses, lalu tiga FAQ untuk landing page atau dua proyek untuk company profile. Pengguna juga harus memilih jenis halaman, gaya, dan status usaha. Setelah itu masih ada pemeriksaan dan persetujuan ringkasan sebelum generation.

Pengumpulan detail ini memang menjaga agar model tidak mengarang isi usaha, tetapi form panjang dan beberapa langkah validasi membuat pengalaman terasa seperti mengisi formulir, bukan memberi satu prompt.

## Temuan tentang model saat ini

- Mini GPT memakai konteks 2.048 token. Batas output source-bound saat ini 896 token untuk `PagePlan` dan 1.536 token untuk setiap `SectionDraft`.
- Generator memproses halaman secara bertahap. Model tidak menulis HTML, CSS, atau JavaScript langsung. Renderer membuat berkas tersebut setelah PagePlan dan SectionDraft lolos validasi.
- `source_bound_plan_prompt` menerima prompt desain serta ID dan jenis fakta. Teks bebas pengguna di prompt tetap menjadi konteks desain, tetapi nilai fakta terstruktur tidak ditambahkan terpisah. `source_bound_section_prompt` menerima ID fakta dan slot yang diizinkan. Resolver memasukkan nilai fakta pengguna ke dalam komponen lokal.
- Checkpoint saat ini dilatih untuk memilih struktur halaman dan memetakan referensi fakta. Belum ada kontrak atau data training yang mengajarkannya mengubah prompt bebas menjadi `RequestDraft`.
- Intake membatasi teks prompt hingga 1.000 karakter. Fakta dari form menggunakan bukti rentang sumber atau konfirmasi langsung pengguna. Batas ini dapat terasa sempit untuk brief yang memuat banyak rincian, tetapi perlu diukur terhadap contoh brief lengkap sebelum menyimpulkan batas efektifnya terlalu kecil.

Kesimpulannya, ukuran konteks bukan satu-satunya hambatan. Model bisa memproses rancangan per bagian, tetapi checkpoint sekarang belum memiliki kemampuan yang dibutuhkan untuk membaca satu prompt bebas dan mengekstrak semua fakta ke dalam draft intake dengan aman. Menghapus form saja tidak akan memperbaiki alur tersebut.

Nilai fakta yang sudah diisi tidak ditambahkan lagi sebagai teks terpisah ke prompt `SectionDraft`; model menerima prompt desain dan referensi terstruktur, lalu resolver lokal memasukkan nilai dari `RequestDraft` ke layout. Karena itu konteks 2.048 token tidak membuktikan checkpoint dapat mengekstrak semua isian dari satu paragraf. Untuk prompt-first, extractor perlu membaca brief dan menghasilkan draft fakta berstruktur. Kapasitas prompt efektif harus dihitung dengan tokenizer setelah mengurangi instruksi schema dan budget output. Batas 4.000 karakter di API hanya batas transport, bukan janji bahwa 4.000 karakter muat dalam satu konteks. Brief yang tidak muat harus ditolak dengan arahan untuk meringkas, tanpa memotong isi diam-diam.

## Tujuan

1. Memungkinkan pengguna menjelaskan halaman melalui satu prompt bebas.
2. Mengubah fakta eksplisit dalam prompt menjadi draft terstruktur yang dapat diverifikasi.
3. Menggabungkan fakta yang kurang dalam satu klarifikasi, tanpa meminta pengguna menyelesaikan field satu per satu.
4. Menyisakan satu tindakan generation yang jelas setelah ringkasan siap.
5. Menjaga validasi source-bound, larangan mengarang fakta bisnis, renderer, preview sandbox, dan unduhan.

## Alur yang diusulkan

```text
Prompt bebas
    -> ekstraksi nilai fakta, lalu pencarian bukti sumber oleh server
    -> validasi RequestDraft dan budget konteks
       -> lengkap: ringkasan singkat, lalu tombol Generate website
       -> kurang: satu pesan berisi seluruh fakta yang masih diperlukan
          -> pengguna menjawab sekali dalam prompt bebas
          -> ekstraksi dan validasi ulang
    -> PagePlan dan SectionDraft bertahap
    -> validasi, resolver, renderer
    -> preview, kode, dan unduhan
```

Untuk tahap pertama, jumlah fakta wajib saat ini tetap dipertahankan: nama, deskripsi, keunggulan, tiga layanan, tiga langkah proses, serta tiga FAQ untuk landing page atau dua proyek untuk company profile. Ini mengurangi isian terpisah dan jumlah giliran, tetapi tidak mengurangi jumlah informasi yang diperlukan untuk halaman lengkap. Itu trade-off yang disengaja untuk melindungi kualitas halaman yang ditargetkan dan mencegah fakta bisnis rekaan. Pengguna dapat menyebutkan semua fakta sekali dalam satu brief bebas. Bila fakta penting belum ada, sistem meminta seluruh kekurangan dalam satu balasan gabungan. Bila masih kurang setelah jawaban itu, tampilkan **Edit detail** yang hanya menampilkan bagian tersisa. Jangan mulai rangkaian pertanyaan satu per satu. Jika setelah mencoba alur ini jumlah informasi wajib masih terasa terlalu banyak, perubahan berikutnya adalah eksperimen terpisah untuk menjadikan sebagian role opsional; eksperimen itu perlu memperbarui kontrak role, catalog, data training, dan development gate.

Jenis halaman dapat dibaca dari kata-kata yang jelas di prompt. Bila tidak dinyatakan, gunakan landing page sebagai nilai awal yang ditampilkan agar mudah diganti. Gaya awal Tailwind dan aset ilustrasi dipilih lokal dari jenis halaman. Status fiktif tidak boleh diasumsikan. Ringkasan menampilkan pilihan **Usaha nyata** atau **Konten fiktif**, belum dipilih secara default. Pengguna harus memilihnya sebelum generation. Pengguna juga dapat membuka detail fakta, memeriksa nilai dan sumbernya, mengeditnya, lalu mengonfirmasi edit sebagai fakta langsung. Jangan membuat nama, deskripsi, layanan, proses, proyek, FAQ, harga, alamat, atau klaim usaha dari asumsi model.

## Kontrak model dan API yang diusulkan

Tambahkan task model khusus `request_extract` pada eksperimen baru. Extractor tidak membuat `RequestDraft` lengkap dan tidak membuat ID fakta atau bukti. Output model memakai schema ekstraksi kecil. Fakta scalar berisi `kind`, satu `value` string, dan `source_message_id`. Fakta terstruktur, seperti layanan, proses, FAQ, atau proyek, berisi `kind`, `title`, `text`, `title_source_message_id`, serta `text_source_message_id`; ini mengizinkan judul dan deskripsi yang dinyatakan di giliran berbeda tetap memiliki provenance masing-masing. Koreksi berisi `kind`, `previous_value`, `replacement_value`, dan frasa koreksi; untuk fakta terstruktur, dua nilai tersebut masing-masing berisi `title` dan `text`. Koreksi juga memuat `source_message_id`; untuk pengganti terstruktur, title, text, dan correction phrase harus berada di pesan koreksi yang sama. Semua nilai dan frasa harus disalin persis dari brief, tanpa parafrasa.

Output extractor memakai enum khusus agar nilai kategori tidak tertukar dengan permintaan fitur:

- `setting_mentions`: satu catatan per mention eksplisit tentang genre atau gaya, berisi `kind` (`genre` atau `style_mode`), nilai enum (`landing_page`/`company_profile` atau `tailwind`/`plain_css`), `phrase`, `context`, `source_message_id`, `occurrence_index`, dan intent `requested`, `retracted`, `negated`, `future`, `reference`, atau `unclear`. `occurrence_index` berbasis nol untuk phrase identik dalam pesan sumber. Phrase diverifikasi server terhadap allowlist alias berversi untuk enum itu. Extractor tidak memilih satu nilai akhir bila ada konflik; server yang menyelesaikan mention menjadi setting draft.
- `capability_mentions`: satu catatan untuk setiap kemunculan frasa yang cocok dengan capability tidak didukung di katalog. Setiap catatan berisi `capability_id`, `phrase`, `context`, `source_message_id`, `occurrence_index`, dan intent `requested`, `retracted`, `negated`, `future`, `reference`, atau `unclear`. `occurrence_index` berbasis nol dan menghitung kecocokan persis `phrase` yang sama dari kiri ke kanan dalam pesan itu. ID wajib berasal dari allowlist `unsupported_capabilities` pada catalog. Genre dan style yang didukung tidak boleh masuk ke daftar ini.
- `out_of_catalog_mentions`: satu catatan untuk setiap permintaan yang tidak didukung katalog, berisi `phrase`, `context`, `source_message_id`, `occurrence_index`, dan intent yang sama. Indeks menghitung kecocokan persis `phrase` yang sama dari kiri ke kanan dalam pesan itu. Ini juga mencakup capability yang tidak punya ID di catalog.

`phrase` dan `context` harus disalin persis dari satu pesan pengguna, dan context wajib memuat kemunculan phrase yang ditunjuk. Server memverifikasi sumber pesan, occurrence index, dan kecocokan substring case-sensitive tanpa normalisasi. Untuk phrase identik yang berulang, indeks mengikat catatan ke kemunculan tertentu; catatan ganda atau hitungan yang tidak cocok dengan pencarian deterministik meminta klarifikasi. Mention dinilai per kemunculan dan ID/kind. Untuk setiap ID unsupported, server memproses mention berdasarkan urutan pesan. `requested` membuat status ID aktif. `retracted` hanya valid jika berada di pesan yang lebih baru daripada permintaan aktif sebelumnya untuk ID/phrase tersebut dan context memuat cue pembatalan dari allowlist berversi, misalnya “batalkan”, “jangan sertakan”, atau “tidak perlu”; status menjadi nonaktif. `negated`, `future`, dan `reference` tidak mengubah status aktif sebelumnya. `unclear` meminta klarifikasi. Jika dalam pesan yang sama ada mention `requested` dan `retracted` untuk ID sama, intake meminta klarifikasi. Mention aktif yang muncul setelah pembatalan mengaktifkan kembali ID itu. Status akhir aktif memblokir generation, sedangkan status akhir nonaktif tidak masuk `RequestDraft.requested_features`. Candidate occurrence unsupported atau setting alias dari catalog yang tidak dipetakan ke catatan extractor juga meminta klarifikasi. Permintaan di luar catalog memakai aturan urutan yang sama: pembatalan harus mengacu pada phrase aktif terdahulu yang cocok persis dan cue pembatalan terverifikasi; mention aktif setelahnya mengaktifkan kembali permintaan. `RequestDraft.requested_features` hanya memuat satu item per ID unsupported yang masih aktif pada akhir riwayat.

Setting yang didukung diselesaikan server dengan aturan sama ketatnya. Mention genre/style yang jelas dan aktif dengan satu nilai unik menetapkan nilai itu. Bila ada mention setting berstatus `unclear`, intake meminta klarifikasi, termasuk bila ada nilai aktif lain. Jika tidak ada mention aktif atau unclear, server memakai `landing_page` dan `tailwind` sebagai default yang dapat diedit. Mention nonaktif seperti negasi, contoh, atau rencana masa depan tidak mengganti setting aktif sebelumnya. Jika pesan baru menegasikan/retract setting aktif terdahulu tanpa memilih pengganti, intake meminta klarifikasi, bukan diam-diam mempertahankan nilai lama atau menerapkan default. Koreksi setting yang eksplisit harus menghubungkan setting aktif terdahulu dengan nilai baru yang disebut di pesan koreksi; koreksi tersebut dapat mengganti nilai. Dua nilai aktif berbeda tanpa koreksi eksplisit menghasilkan `needs_clarification`. Nilai paling baru tidak menang otomatis. Setting phrase harus cocok dengan alias berversi untuk enum; frasa untuk jenis/gaya di luar daftar dialihkan ke `out_of_catalog_mentions`.

Server memetakan field scalar ke nilai fakta scalar dan `title`/`text` ke struktur fakta intake. Scalar menyertakan satu `source_message_id`; fakta terstruktur menyertakan ID sumber per field. Model tidak membuat ID fakta atau rentang. Server membuat ID, mengisi properti nonfakta, memastikan setiap nilai ada persis di pesan sumber field itu, lalu mencari rentang sumber dan mengisi bukti. Judul dan deskripsi boleh berasal dari pesan berbeda, tetapi masing-masing harus memiliki kecocokan persis. Bila nilai identik berulang pada pesan yang sama, server memilih kemunculan pertama secara deterministik. Nilai list identik dideduplikasi dan tidak dihitung sebagai beberapa fakta wajib. Untuk setiap capability aktif yang dikenal, server membentuk `{capability_id, evidence: {source_span: {start, end, quote}}}` dengan satu item per ID; `quote` harus sama dengan source span dan frasa harus cocok case-insensitive dengan satu `evidence_phrases` catalog. Rentang pada `RequestDraft` memakai indeks string Python yang dipakai validator. Respons intake juga menyertakan `source_message_id`, rentang pesan lokal UTF-16 untuk UI JavaScript, kutipan persis, dan rentang kanonis Python untuk tiap field fakta. Ini membuat kutipan dapat disorot di browser tanpa mengubah kontrak validator. Nilai fakta atau bukti yang tidak cocok ditolak atau dilaporkan sebagai kekurangan. Server membentuk `IntakeExtractResponse` dengan draft, bukti, konflik, dan sumber pesan. Output model malformed atau inference error tidak menghasilkan draft siap-generation; API memberi error terkontrol dan UI mempertahankan brief dengan opsi coba lagi atau edit detail. Permintaan unsupported aktif selalu memblokir generation.

Browser mengirim riwayat sebagai `messages` terstruktur dengan ID stabil dan isi teks asli. Server menetapkan jenis pesan berdasarkan urutan sesi (`initial` untuk pesan pertama, `additional` untuk jawaban berikutnya), membuat tabel rentang pesan, lalu menghasilkan `canonical_prompt` memakai formatter versi tetap. Batas pesan tidak pernah ditebak dengan memecah teks. Teks pesan tidak dipangkas, dinormalisasi, atau diubah. Extractor menerima struktur pesan yang sama dalam serialisasi JSON kompak yang memuat ID, jenis, dan teks; contoh training extractor memakai format identik. Generator, `RequestDraft.prompt`, validasi, dan generation memakai satu `canonical_prompt` hasil server dari pesan dan urutan yang sama. Jadi isi sumber dan urutan konsisten lintas tahap, sementara representasi input model extractor memang berupa JSON terstruktur, bukan string kanonis generator. Segment map dan teks mentah dari request tetap menjadi sumber kebenaran server. Response provenance mengembalikan ID pesan dan rentang UI UTF-16 hasil konversi dari indeks Python untuk setiap nilai fakta. Model wajib menyebutkan ID pesan asal untuk tiap field fakta, mention capability, serta koreksi, dan server memastikan nilai memang ada di pesan yang dirujuk. Jika nilai single-valued berbeda dan tidak ada koreksi yang jelas, sistem menandainya sebagai konflik dan meminta pengguna memilih.

Untuk semua koreksi, extractor mengeluarkan `kind`, `previous_value`, `replacement_value`, `correction_phrase`, dan `source_message_id` pesan koreksi. Nilai scalar fakta lama harus sama persis dengan satu fakta scalar terdahulu. Untuk fakta terstruktur, nilai lama dan pengganti masing-masing berupa `{title, text}` dan nilai lama harus cocok ke tepat satu item terdahulu. Untuk koreksi genre/style, `previous_value` dan `replacement_value` adalah enum; nilai lama harus sama dengan setting aktif yang telah diselesaikan dari riwayat sebelumnya, bukan sekadar mention nonaktif atau historis. Nilai pengganti atau phrase setting serta frasa koreksi wajib ditemukan pada pesan sumber koreksi yang sama. Server memastikan pengganti masuk ke draft akhir dan mencatat rentang bukti setiap field `title` dan `text` secara terpisah. Jika nilai lama tidak cocok ke tepat satu fakta sebelumnya, item list ambigu, atau pengguna hanya meminta penghapusan sehingga jumlah fakta wajib berkurang, intake meminta konfirmasi atau fakta pengganti. Koreksi eksplisit seperti “koreksi”, “bukan X, tetapi Y”, atau “yang benar Y” dapat mengganti nilai scalar. Untuk fakta list-valued, koreksi eksplisit mengganti satu item utuh dengan item baru. Fakta list lain tetap dipertahankan.

Tambahkan endpoint `POST /api/v1/intake/extract` dengan request JSON konseptual:

```json
{
  "canonical_format": "prompt-messages-v1",
  "messages": [
    {"id": "m1", "text": "..."},
    {"id": "m2", "text": "..."}
  ]
}
```

Server menolak versi format yang tidak dikenal, ID pesan duplikat, teks kosong yang tidak diizinkan, atau riwayat melebihi batas transport. Ia membuat `canonical_prompt` dan segment map dari pesan terstruktur. Input `request_extract` memuat ID itu secara terlihat melalui serialized structured-message JSON yang sama dengan contoh training, bukan melalui prompt datar yang kehilangan batas sumber. Respons memakai schema baru `IntakeExtractResponse`, bukan `IntakeResponse.request`: `status`, `message`, `missing_fields`, draft parsial yang dibentuk server, bukti yang dapat diperiksa, konflik, dan permintaan unsupported bila ada. Status mencakup `ready`, `needs_clarification`, `unsupported`, dan error terkontrol yang tidak berisi draft valid. Endpoint ini hanya menyiapkan intake, tidak membuat berkas website. Output model malformed atau inference error tidak boleh diperlakukan sebagai draft parsial valid. Pertahankan `POST /api/v1/intake/validate` untuk koreksi draft yang dibuat pengguna, dan pertahankan validasi server pada `POST /api/v1/generations`.

Runtime menggunakan satu lock inferensi dan memuat extractor serta generator secara bergantian, bukan mengasumsikan keduanya menetap bersama di VRAM. Ekstraksi memakai checkpoint extractor; generation tetap memakai checkpoint TRAIN-025 step 1800 yang terpilih. Status health melaporkan konfigurasi dan status muat masing-masing model. Development preflight mengukur peak VRAM, waktu muat, dan pelepasan model; jika perilaku bergantian tidak stabil, fitur extraction tidak dipromosikan dan intake manual tetap tersedia.

Selaraskan batas pada textarea, Pydantic API, JSON Schema, dan generation request. Gunakan batas keras 4.000 karakter untuk brief gabungan, tetapi hitung batas efektif dengan tokenizer untuk setiap permintaan. Ukur persis serialisasi JSON pesan yang diterima extractor, instruksi schema, dan budget output; jangan memakai panjang karakter sebagai pengganti token. Tetapkan budget output setelah mengukur schema ekstraksi maksimum pada contoh train dan development, bukan dari ukuran `RequestDraft` yang dibuat server. Bila tidak muat, ukur ulang budget atau schema tanpa memotong fakta. Brief yang melewati budget ditolak dengan pesan ringkas agar pengguna memadatkan keterangannya. Jangan menaikkan context window tanpa checkpoint dan eksperimen terpisah.

### Implementasi budget 2048 token

Preflight terhadap contoh TRAIN-025 keluarga `family0000` mengukur satu brief utuh sebesar 1.221 prefix token dan satu output lengkap sebesar 1.723 token. Keduanya tidak dapat berada dalam konteks 2.048 token. Karena itu, satu permintaan API menjalankan task `request_extract` berulang secara berurutan dalam 16 scope tetap: `business_scalars`, `service_1` sampai `service_3`, `process_1` sampai `process_3`, `faq_1` sampai `faq_3`, `project_1` sampai `project_2`, `page_settings`, `business_status`, `capabilities`, dan `corrections`. Layanan, proses, FAQ, dan proyek dipisah per posisi agar satu jawaban panjang tidak membuat seluruh daftar melewati budget; koreksi eksplisit mengganti item di posisi asalnya. Setiap call menerima riwayat pesan terstruktur yang sama beserta `extract_scope`; setiap output tetap memakai schema `request-extract-v1`, tetapi array di luar scope wajib kosong. Server menggabungkan output hanya setelah semua scope tervalidasi. Pada corpus train/development, `page_settings` memiliki keluaran terbesar sebesar 502 token, budget 543 token setelah margin, dan prefix terbesarnya 1.409 token. Kombinasi terberat itu berjumlah 1.952 token, masih di dalam konteks 2.048. Prefix maksimum lintas scope adalah 1.446 token pada `faq_1`; budget scope tersebut 238 token. Ini berarti satu request API dapat memerlukan hingga 16 decode internal dan menambah latensi, tetapi tidak menambah pesan atau klarifikasi yang dilihat pengguna. Jika salah satu scope melampaui konteks atau gagal divalidasi, seluruh ekstraksi ditolak dan editor manual tetap tersedia.

## Training dan evaluasi sebelum integrasi

- Buat contoh `request_extract` hanya dari keluarga data training dan fakta yang sudah tersedia. Bekukan manifest development baru sebelum membuat contoh extractor. Keluarga fakta dan pola prompt development harus berbeda dari data training, selection, dan augmentasi TRAIN-025, serta dari training, selection, dan augmentasi extractor. Manifest menyimpan ID keluarga sumber dan pola prompt untuk setiap partisi, hash manifest yang dibekukan, serta hitungan keluarga unik per bucket. Skrip audit wajib membuktikan irisan keluarga dan pola prompt kosong sebelum training dan sebelum scoring; hitung keluarga unik, bukan baris/augmentasi. Jika audit gagal atau manifest berubah, gate development gagal. Development tidak boleh digunakan untuk prompt tuning atau memilih checkpoint; jika dipakai untuk itu, buat development baru yang belum dilihat. Sertakan prompt lengkap, prompt tidak lengkap, koreksi eksplisit, fakta berulang atau bertentangan, negasi, klaim masa depan, capability katalog yang unsupported, dan permintaan di luar catalog. Keluaran berisi nilai sumber persis, dan server pengembangan membuktikan nilai itu memang ada di pesan yang ditunjuk.
- Buat checkpoint extractor kandidat terpisah yang diinisialisasi dari TRAIN-025 step 1800. Checkpoint generator pilihan aplikasi tidak ditimpa dan tetap bertanggung jawab atas PagePlan serta SectionDraft. Ukur lebih dulu biaya memori saat extractor dan generator dipakai bergantian; jangan mengasumsikan keduanya harus berada di VRAM bersama-sama.
- Sediakan sedikitnya 100 contoh dari keluarga berbeda untuk tiap jenis fakta dan sedikitnya 100 brief untuk masing-masing jenis halaman. Sediakan sedikitnya 50 keluarga berbeda untuk setiap bucket keselamatan: input tidak lengkap, koreksi single-valued, koreksi list-valued, konflik ambigu pada fakta atau setting genre/style, negasi atau klaim masa depan, capability katalog unsupported, permintaan di luar catalog, pembatalan capability aktif known-catalog, pembatalan permintaan aktif out-of-catalog, serta retraction genre/style tanpa nilai pengganti. Jika jumlah keluarga independen tidak tercapai, hasil bucket bersifat diagnostik dan tidak boleh dianggap lulus gate. Ukuran ini adalah minimum bukti operasional, bukan jaminan confidence statistik.
- Ukur precision exact-value per field yang diterima, recall terhadap fakta eksplisit, koreksi, pembatalan, dan konflik yang ditangani benar, penolakan klaim unsupported, abstain saat input kurang, serta false rejection. Unit untuk gate keselamatan adalah keluarga prompt unik. Known-catalog false-rejection rate = keluarga dengan minimal satu mention known-catalog nonaktif, tanpa mention unsupported aktif dan tanpa intent unclear, yang hasil API-nya `unsupported`, dibagi seluruh keluarga dengan kondisi tersebut. Unknown/out-of-catalog false-rejection rate dihitung terpisah dengan rumus sama untuk mention di luar catalog. Retraction-overblocking rate dihitung terpisah untuk keluarga yang membatalkan permintaan aktif terdahulu tanpa permintaan aktif ulang, tetapi tetap mendapat status `unsupported`, dibagi seluruh keluarga pembatalan tersebut. Unclear-rejection rate = keluarga dengan intent unclear, tanpa mention aktif, yang hasilnya `unsupported`, dibagi seluruh keluarga dengan kondisi tersebut; hasil yang benar untuk intent unclear adalah `needs_clarification`. Keluarga setting genre/style yang diretract tanpa pengganti harus menghasilkan `needs_clarification`; gate bucket ini 100 persen. Keluarga campuran yang memuat mention aktif setelah pembatalan dikeluarkan dari denominator retraction dan dilaporkan terpisah. Setiap denominator harus memiliki minimal 50 keluarga unik; jika tidak, bucket hanya diagnostik dan tidak lulus gate. Gate awal yang diusulkan adalah precision sedikitnya 95 persen, recall sedikitnya 90 persen, nol fakta tanpa bukti valid yang lolos, sedikitnya 95 persen koreksi eksplisit dan pembatalan diterapkan benar pada bucket scalar, list, genre/style, serta capability, 100 persen konflik single-valued ambigu ditahan untuk konfirmasi, nol permintaan unsupported yang masih aktif lolos ke generation, dan paling banyak 5 persen false rejection serta retraction-overblocking pada masing-masing denominator nonaktif di atas. Laporkan juga hasil per jenis fakta, genre, dan bucket kasus, bukan hanya angka gabungan. Setelah itu, teruskan draft hasil ekstraksi melewati validasi dan generation dev yang sama; kandidat hanya dapat diterima jika gate generation yang ada tetap lulus. Final tetap tertutup.
- Integrasikan extractor hanya jika seluruh fakta yang diterima lolos pemeriksaan bukti dan kandidat memenuhi gate development yang disetujui. Jika gagal, UI tetap menyediakan panel detail manual dan tidak berpura-pura prompt bebas sudah dipahami.
- Jangan menyatakan target kualitas visual 95 persen lulus hanya dari validasi struktur atau akurasi ekstraksi. Penilaian visual tetap membutuhkan review browser dan manusia.

## Kriteria penerimaan

1. Pengguna dapat memasukkan brief dalam satu prompt tanpa formulir multi-bagian pada awal sesi.
2. Semua fakta yang diterima otomatis memiliki rentang sumber valid yang menunjuk brief kanonis; UI dapat menunjukkan kutipan dan pesan asal.
3. Fakta yang kurang dilaporkan sekaligus dalam satu balasan. Setelah satu jawaban tambahan yang belum cukup, pengguna mendapat editor detail, bukan pertanyaan berulang.
4. Generator tidak membuat klaim bisnis yang tidak ada di sumber.
5. Generation hanya dimulai setelah pengguna menekan **Generate website** dan validasi server lulus.
6. Hasil lengkap tetap menggunakan pipeline source-bound, validator, resolver, dan renderer yang ada.
7. Preview, kode, unduhan, responsif, aksesibilitas keyboard, dan penyimpanan sesi tetap berfungsi.
8. Model ekstraksi yang belum lulus development tidak boleh menjadi jalur default aplikasi.

## Di luar cakupan

- Mengganti backbone atau memperbesar context window.
- Mengirim prompt ke penyedia model cloud.
- Mengubah format output website, renderer, atau sistem ZIP.
- Membuka atau menggunakan partisi final untuk penyetelan.
- Menjanjikan isi lengkap dari prompt yang tidak memiliki fakta wajib.

## Keputusan pengguna

Pengguna menyetujui extractor Mini GPT menerima isi pesan prompt dan klarifikasi secara terstruktur beserta ID sumber. Server akan membentuk satu `canonical_prompt` untuk `RequestDraft`, validasi, dan generation dari isi serta urutan pesan yang sama. Setiap fakta harus menunjuk ke sumbernya; fakta, setting, atau capability yang konflik tidak dipilih diam-diam. Status usaha nyata atau fiktif harus dipilih. Satu ringkasan menampilkan sumber tiap fakta dan satu tombol generation. Runtime menukar checkpoint satu per satu. Batas brief keras 4.000 karakter tetap tunduk pada budget tokenizer yang lebih kecil. Layout percakapan dan preview dibuat lebih lapang. Pengguna memilih mempertahankan semua fakta wajib sambil menyederhanakan langkah dan jumlah giliran.
